# 07 世界の都市にマウスを乗せる

## 依頼

> 世界の都市（Natural Earth の populated places、約 7,300 都市）を人口に応じた大きさの点で表示して、マウスを乗せた都市の名前と人口を出したい。ノート PC のブラウザで使う。ページ全体（コードとデータ）で gzip 150 KB 以内にしたい。

## 読み取った要件

| 要件 | 数値にしたもの (spec.yaml の evaluation.budgets) |
| --- | --- |
| ページ全体で gzip 150 KB 以内 | コード (index.html + main.ts + cities.ts) とデータの gzip 後の合計 total_gzip_bytes 150,000 B 以下 (作った時点のハーネスには合計がなく 6,000 B と 144,000 B に割っていたが、のちに合計の指標を足した) |
| ノート PC のブラウザ | 1280×800、DPR 2 (いまのノート PC の多く)、CPU 2 倍スロットル (計測機より遅い CPU の代わり) |
| すぐ出る | 初回描画 p50 400 ms 以下 |
| 動かしても引っかからない | 世界全体から欧州へ 32 倍ズームして戻る 300 フレーム、世界全体の固定視点、欧州 32 倍の固定視点で、GPU 完了までの frame_ms p95 各 8.3 ms 以下 (120 Hz) |
| マウスを乗せたらすぐ出る | 当たり判定とツールチップ更新で hover_ms p95 1 ms 以下 |
| 約 7,300 都市のどれにでも乗せられる | 各都市を 32 倍で画面中央に置き、中央で拾われるのがその都市である割合 reachable_ratio 0.99 以上 |
| 正しく出ている | 機能確認: 世界全体で全都市の中心ピクセルに何か描かれている、グリーンランドは陸の色、太平洋は海の色。東京の上で実際に pointermove を送り、ツールチップが「東京都 (日本) 人口 35,676,000 人」で、中心ピクセルが強調色。太平洋の上ではツールチップが空 |

人口に比例した「大きさ」は面積で読む: 半径は √人口 に比例 (東京 3,568 万人で 18 CSS px、最小 1.5 px)。大きさはズームしても変えないので、凡例 (10 万、100 万、1,000 万) がいつでも正しい。

## やらないこと

地図上の文字、国境、タイル、回転、3D、実行時の投影計算、タッチ操作 (ピンチ)、クリックでの選択、検索、海岸線の詳細 (陸は 4 倍ズームまでの精度、それより寄ると粗く見える)。ズームとパンは依頼にないが、世界全体では 72% の都市しか上に出ないので入れた (ホイールとドラッグだけ)。

## 設計

- 03 (地震の再生) から始めた。PC、陸の上に点、ホイールとドラッグ。
- Equal Earth にベイク時に投影し、16 ビットに量子化する (32 倍ズームで 1 段 0.6 CSS px)。
- 陸は国を ogr2ogr (ST_Union) で 1 つに溶かしてから単純化する。国のままだと共有境界を 2 回配ることになり、同じ許容誤差で 62 KB が 43 KB になった。
- 陸は三角形分割せず、リングの頂点と頂点数だけを配る。読み込み時にリングごとの扇 (fan) を作り、ステンシルの INVERT で偶奇塗りする。穴 (カスピ海など) も自然に抜ける。インデックスを配っていた最初の版は陸だけで 88 KB gzip だった。
- 都市は描く順にベイクする: 大きい点から先、同じ半径の中では Morton 順。小さい点が大きい点に隠れない。同じ半径の中の順番は見た目に出ないので、Morton 順にして位置の差分を小さくした。人口の降順そのままより位置が 4.9 KB 小さく、人口列が 1.3 KB 大きく、差し引き 3.6 KB 減った。
- 半径はベイク時に 0.1 px 単位で 1 バイトにして配る。シェーダと当たり判定が同じ値を使う。
- 名前は UTF-16LE のテキスト 1 本 (国名、空行、都市名)。UTF-8 の JSON より 2 KB 小さく、`TextDecoder` で 1 行で読める。国名は Natural Earth 国データの NAME_JA を ADM0_A3 で引き、無い 3 つ (南スーダン、スヴァールバル、トケラウ) はベイクに書いた。
- 当たり判定は CPU の総当たり。描画順の最後 (いちばん上) から見て、円 (最低 2 CSS px) がカーソルを含む最初の都市。7,342 件を毎回なめても p95 0.3 ms で、索引はいらなかった。見えている一番上の点が拾われるので、東京の円の中心付近では、上に重なる川崎市などが出る。東京は円の外周寄りで拾える。
- 描くのは何かが変わったときだけ (rAF を 1 回予約)。強調は同じ点を 1 個だけもう一度描く。
- 計測用コードは bench.ts に分け、`?bench` のときだけ読み込む。index.html はページ全体の予算に入れるため footprint に含めた。

## 計測で分かったこと

- データ gzip 132,600 B (陸 43,024、都市 49,340、名前 40,240)、コード 4.4 KB 前後。合計約 137 KB で 150 KB に収まる。生のままだと転送 294 KB (計測用の静的サーバは gzip しない)。
- 最初の hover_ms は毎回 2 個目のサンプルだけ 30〜39 ms だった。初めて `toLocaleString('ja-JP')` を呼んだときの ICU データの初期化 (単独で測って 34 ms、2 回目は 0.17 ms)。正規表現で 3 桁区切りにして消した。
- 中心ピクセルの機能確認を「都市の色 (橙) か」にしたら 7,342 中 536 が落ちた。密集地で隣の小さな都市の白い縁が中心にかかるためで、描画は正しかった。「陸の色でも海の色でもない」に変えた (橙のままなのは 92.7%)。
- 到達できる都市: 1 倍で 72.4%、32 倍で 7,341/7,342。ベイク時の総当たりで、最低 2 px の当たり半径なら 32.5 倍でちょうど全部になると見積もっていたのと合う。
- 計測中、同じ機械で別の処理が走っていて load average が 70〜120 あった。first_frame_ms は load 124 のとき 5 回で 120〜458 ms (p50 174)、load 72 のとき 73〜176 ms (p50 76) で、どちらも最初の 1 回が遅い。GPU 時間 (gpu_ms p95) は 1.2〜1.7 ms で負荷に関係なく安定していた。時間の予算は負荷の低いときに測り直す価値がある。
- 修正後の最終計測 (load 72): frame_ms p95 2.6 ms、whole 1.77 ms、deep 2.15 ms、hover_ms p95 0.25 ms、JS ヒープ 2.1 MB。
