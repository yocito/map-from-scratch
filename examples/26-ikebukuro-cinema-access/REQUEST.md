# 26 グランドシネマサンシャインへの案内図

## 依頼

> 池袋のグランドシネマサンシャインの場所をわかりやすく説明する地図を作りたい

途中で追加の依頼があった。

> 目印になる建物がポイントポイントでどんなふうに見えるのか、シミュレーションしてレンダリングして挿入できる？

## 読み取った要件

| 要件 | 数値にしたもの (spec.yaml の evaluation.budgets) / 確かめ方 |
| --- | --- |
| 目的地の建物がひと目でわかる | 建物を赤で塗り、映画館名と建物名を横に出す。`dest-highlighted` と `dest-label-drawn` で画面のピクセルを確かめる |
| 池袋駅からの道順がわかる | 東口(中央)からの徒歩経路を地図に引き、道順と徒歩時間を文章で出す。`route-drawn`、`start-goal-markers`、`directions-shown` |
| 途中の目印の見え方がわかる | 経路上の 3 地点から目の高さで見た立体の模式図を出す。`views-drawn` |
| スマホで文字が読める | 390 px 幅で最小の文字 11 px 以上、ラベルの重なり 0 |
| 重くならない | コード gzip 4.5 KB 以下、データ 35 KB 以下、合計 40 KB 以下 |
| すぐ出る | 4G・CPU 4 倍スロットルで初回描画 p50 600 ms 以下 |
| サイズ変更ですぐ描き直す | 変更から描き直したフレームまで p95 100 ms 以下 |

## やらないこと

パン、ズーム、回転、視点を動かせる 3D、屋根や壁の質感、タイル、実行時の投影と経路探索、現在地、地下通路と館内の案内、WebGL。縮尺と範囲を固定した 1 枚の案内図と、固定の視点からの 3 枚の模式図だけを描く。

## 設計

- **データ**: OSM 東京 23 区の GeoParquet (yuiseki/osm-tokyo23-src-2026-08) を、ベイク時に HTTP Range で読む。フッターの行グループ統計 (bbox 列) で枠に触れる行グループだけを読み、102 個中 25 個で済む。そのための Parquet 読み取り器 `tools/parquet.ts` を、`kits/geoparquet` の Thrift と Zstd の上に書いた (PLAIN と辞書エンコーディング、データページ v1/v2)。
- **目的地の特定**: 名前の記憶には頼らない。OSM の amenity=cinema「grand cinema sunshine」のノードを含む建物がグランドスケープ池袋 (way 705716220) であることをデータで確かめた。最初の案で記憶から書いた「キュープラザ池袋」は誤りだった。
- **地図**: 東口と映画館の中間を中心にした 700 m 四方を 1,000 単位のグリッドに一次変換し、面 6 層と線 5 層を層ごとに 1 本の SVG パス文字列にする。ブラウザは `Path2D` に渡して塗るだけ。
- **経路と道順**: 歩ける道のグラフ (地下は除く) で、東口(中央) の駅出口ノードから建物の外周までを Dijkstra で求める (460 m、80 m/分で 6 分)。道順の文章は経路の辺を通り名でまとめ、横断歩道は交わる道路名で「〜を渡る」にする。
- **ラベル**: 縮尺が固定なので、配置はベイク時に決める (文字の大きさはグリッド単位)。目的地、出発点、通り名、目印の順に貪欲に置き、ラベル同士・目的地・ルートの線と重ならない候補を選ぶ。通り名は同名の way をつないだ直線区間に、ルートが通る道ではその脇に置く。
- **目線の立体図**: 経路上の 3 地点 (東口を出たところ、サンシャイン通りに入ったところ、建物の 90 m 手前) に高さ 1.6 m、水平画角 72° のカメラを置く。建物の壁の透視投影、裏面の除去、近クリップ面と画面でのクリップ、建物単位の画家のアルゴリズムをベイク時に済ませ、ページは画面座標の多角形を順に塗るだけにした。見えている建物の名前は、ベイク時に最前面の多角形を点ごとに調べて決める。地図の下にあるので、データは別ファイル `views.json` にして地図の表示後に読む。

## 計測で分かったこと

このコンテナ (GPU なし、Chromium のソフトウェア描画) で `node harness/cli.ts bench 26-ikebukuro-cinema-access -n 5` を実行した結果。

| 指標 | 値 | 予算 |
| --- | --- | --- |
| 初回描画 p50 | 550 ms | 600 ms |
| 立体図が出るまで p50 | 926 ms | (記録のみ) |
| コード / データ / 合計 (gzip) | 3.7 / 29.4 / 33.0 KB | 4.5 / 35 / 40 KB |
| 最小の文字 | 11.5 px | 11 px 以上 |
| ラベルの重なり | 0 | 0 |
| リサイズ後の描き直し p95 | 232-446 ms (実行ごとにばらつく) | 100 ms (未達) |

- 検証チェック 6 つ (目的地の強調、目的地の名前、ルート、出発点と到着点、道順の文章、立体図) は 5 回すべてで通った。
- リサイズの予算は未達。1 層ずつ測ると、道路 64 ms、建物 30-41 ms、破線の鉄道 31 ms (実線で 14 ms) で、ソフトウェアでのラスタ化そのものが重い。GPU のある計測環境 (`bin/mfs bench`) ではまだ測っていない。
- 1,040 m 四方の最初の版は経路が細い帯になり、建物も小さかった。700 m 四方に寄せると、地図のデータも 75.0 KB から 37.1 KB (gzip 14.9 KB) に減った。
- 立体図を地図と同じファイルで先に描くと、初回描画が 975 ms に遅れた。別ファイルで後から読むと 550 ms。
- 初回描画を `bench.ts` 側で測ると、`bench.ts` の読み込み (4G で約 1 往復) まで数えてしまう。ページ側の `performance.mark('map-shown')` で測るようにした。
- 高さのタグがある建物は 41% だけで、残りは 4 階建てと仮定している。立体図は模式図であることをページに書いた。
