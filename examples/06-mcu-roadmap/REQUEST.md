# 06 マイコンで渋谷の道路地図

## 依頼

> ESP32-C6（RISC-V 160MHz、RAM 512KB、FPU なし、PSRAM なし）と 240x240 の液晶のハンディ端末で、渋谷駅のまわりの道路地図をボタンでスクロール・拡大縮小したい。

## 読み取った要件

| 要件 | 数値にしたもの |
| --- | --- |
| RAM 512 KB、PSRAM なし | 描画器のグローバル変数 0 バイト (rv32 の .data + .bss)。フレームメモリは 16 行分のストリップ 7,680 バイトだけ |
| FPU なし | 整数演算だけ。描画器のオブジェクトが自分のデータ以外のシンボルに依存しないことをビルド時に確かめる (libgcc の浮動小数点や 64 ビット除算を呼んでいたら失敗する) |
| フラッシュに収まる | 描画コード (.text) 4 KB 以下、道路データ (.rodata) 1 MB 以下 |
| ボタンでスクロール・拡大縮小 | 5 段のズーム (1 ピクセル 5.3 m〜0.33 m) のそれぞれで、1/16 画面ずつ正方形を描くように動かす 400 フレーム |
| 正しく描けている | データ中の高速道路の点を画面中央に置き、そのピクセルが高速道路の赤 (RGB565 0xE30B) であることを確かめる |

## やらないこと

フルフレームバッファ、浮動小数点、malloc、libc、アンチエイリアス、文字、面、タイル、実行時のデータ読み込み (データはフラッシュの const 配列としてリンクする)。

## 設計

- 描画器 (`mcumap.c`) は freestanding。libc もヒープも浮動小数点も、書き換わるグローバル変数もない。呼ぶ側は 240×16 の RGB565 バッファを 1 本だけ持ち、ストリップを描くたびに LCD へ送る。
- 座標は渋谷駅を原点とする 0.5 m 単位の int16。道路はベイク時に駅から 3.1 km の正方形で切り取る。座標が小さいので、クリッピングの積は int32 に収まる (範囲は `mcumap.h` に書いた)。64 ビット除算 (`__divdi3`) を使わないので、ライブラリをリンクしなくて済む。
- 道路ごとに外接矩形をベイクし、ストリップに掛からない道路は、線分を調べずに飛ばす。ズームアウト時は生活道路と歩道 (種別 3 と 4) を描かない。
- 線分は Cohen–Sutherland でストリップに切り詰めてから Bresenham で描き、太さは種別ごとの正方形ブラシ (1〜3 px)。
- データは `roads_data.c` (1 行 1 道路) として生成し、フラッシュの const 配列としてリンクする。

## 計測で分かったこと

- rv32imc -Os で描画コードは 988 バイト、RAM 0 バイト。道路 12,878 本と点 68,495 個のデータは 480 KB。
- ホストでの 1 フレームは p50 0.28 ms。これは端末の時間ではない。端末でも変わらない仕事量 (1 フレームに描いた区間数 p95 3,609、書いたピクセル数 p95 47,540) を一緒に記録している。
- ズームインした 3 段では、ストリップごとに全道路の外接矩形を試している (1 フレーム 193,170 回)。実際に描く区間は 600〜2,700 で、試行のほとんどは、描く区間につながらない。端末で遅ければ、次は「格子 × 種別」の道路リストをフラッシュにベイクして試行を減らす。実機での計測は端末をつないで行う (Human in the loop)。
